# แยกหน้าบ้านกับระบบภายในแบบสองเครื่อง (ขั้นสูง)

เอกสารนี้สำหรับผู้ดูแลที่เลือกรูปแบบ "ขั้นสูง: แยกสองเครื่อง" ตัวติดตั้งติดตั้งให้เฉพาะฝั่งที่เปิดบนเครื่องนั้น ส่วนจับคู่ เครือข่าย และการป้องกันเพิ่มเติม ผู้ดูแลทำเอง ถ้าใช้เครื่องเดียว ให้เลือกรูปแบบ "มาตรฐาน" ตัวติดตั้งทำทุกอย่างในเอกสารนี้ให้อัตโนมัติ (ยกเว้นการแยกสิทธิ์ระบบปฏิบัติการ หัวข้อ 7 และ cron)

## 1. ติดตั้งอะไรที่ไหน

| เครื่อง | ฝั่ง | ชื่อ | เก็บอะไร |
| --- | --- | --- | --- |
| A (ในเครือข่ายโรงเรียนหรือเครื่องที่ล็อกแน่น) | ระบบภายใน | `app.school.ac.th` | หลังบ้าน CMS งานโรงเรียนทั้งหมด ข้อมูลนักเรียน บัญชีเจ้าหน้าที่ และกุญแจลับของการจับคู่ |
| B (เครื่องสาธารณะ) | หน้าบ้าน | `www.school.ac.th` | เนื้อหาที่เผยแพร่แล้ว ฟอร์มสาธารณะ กล่องรับเรื่องแบบเข้ารหัส ไม่มีข้อมูลภายใน |

ขั้นตอน

1. ใช้ชุดติดตั้งเวอร์ชันเดียวกันทั้งสองเครื่อง (ไฟล์ `VERSION` ต้องตรงกัน)
2. เครื่อง A: เปิด `/install/` เลือก "ขั้นสูง" แล้วเลือกฝั่ง "ระบบภายใน" กรอกฐานข้อมูลของเครื่อง A
3. เครื่อง B: เปิด `/install/` เลือก "ขั้นสูง" แล้วเลือกฝั่ง "หน้าบ้าน" กรอกฐานข้อมูลของเครื่อง B ฝั่งนี้ไม่มีบัญชีผู้ดูแล
4. ทั้งสองเครื่องต้องเป็นฐานข้อมูลคนละชุดบนเซิร์ฟเวอร์ฐานข้อมูลของตัวเอง ห้ามใช้ฐานข้อมูลหรือผู้ใช้ DB ร่วมกัน
5. ตั้ง DocumentRoot ของแต่ละเครื่องไปที่โฟลเดอร์ `public/` ของแอปนั้น

ตัวติดตั้งเขียน `SAAN_EDITION` (`internal` หรือ `public`) และรหัสติดตั้ง `SAAN_INSTALL_ID` ใน `.env` ให้เอง รหัสนี้ใช้ต่อท้ายชื่อคุกกี้ เซสชัน แคช ล็อก คิว และชื่อไฟล์สำรอง ใช้ซ้ำกับเครื่องอื่นไม่ได้

## 2. จับคู่ผ่าน HTTPS

หน้าบ้านต้องรู้กุญแจสาธารณะของระบบภายใน และระบบภายในต้องรู้ที่อยู่รับข้อมูลของหน้าบ้าน กุญแจลับไม่ออกจากเครื่อง A

1. เครื่อง B: `php artisan saan:pair-token` (หรือใช้คำสั่งในข้อ 3 โดยตรง)
2. เครื่อง A: เข้า `/admin/pairing` ออกรหัสจับคู่ (ใช้ครั้งเดียว อายุ 15 นาที ผูกกับที่อยู่ `https://www.school.ac.th/_saan/push`)
3. เครื่อง B: `php artisan saan:pair https://app.school.ac.th <รหัส>`
4. เครื่อง A: `php artisan saan:publish --full` ส่งข้อมูลชุดเต็ม แล้วตรวจด้วย `php artisan saan:publish --verify`
5. ตรวจ `php artisan school:doctor` ทั้งสองเครื่อง ต้องไม่มี `[ERR]`

ข้อควรระวัง: การจับคู่ต้องใช้ HTTPS เท่านั้น (http ยอมเฉพาะ localhost) ระบบไม่ตามการ redirect เพื่อไม่ให้รหัสไปที่อื่น

### ถ้าฝั่งหน้าบ้านไม่มี SSH: ใช้แบบฟอร์มบนเว็บแทนคำสั่ง saan:pair

ขั้นที่ 1 และ 3 ทำผ่านเว็บได้ (ขั้นที่ 2 ออกรหัสที่ระบบภายในเหมือนเดิม)

1. File Manager ของหน้าบ้าน: สร้างไฟล์ `storage/app/private/saan-pair.token` ใส่รหัสเจ้าของเครื่องที่ตั้งเองบรรทัดเดียว ยาวอย่างน้อย 32 ตัวอักษร ใช้ `A-Za-z0-9_-` และมีตัวอักษรต่างกันอย่างน้อย 16 ตัว (ถ้ามี SSH `php artisan saan:pair-token` สร้างให้ และ `--remove` ลบ)
2. ระบบภายใน `/admin/pairing`: ออกรหัสจับคู่
3. เปิด `https://www.school.ac.th/_saan/setup` กรอก รหัสเจ้าของเครื่อง ที่อยู่ระบบภายใน และรหัสจับคู่ แล้วกด จับคู่
4. สำเร็จแล้วไฟล์ `saan-pair.token` ถูกลบเอง ระบบภายในส่งข้อมูลชุดเต็มมาภายใน 1-2 นาที (ต้องมี cron ฝั่งระบบภายใน) รหัสผิด 10 ครั้งจากเครือข่ายเดียวกันถูกล็อก 15 นาที ไม่มีไฟล์นี้หน้า `/_saan/setup` ตอบ 404 และ `school:doctor` เตือนถ้าไฟล์ค้างเกินหนึ่งชั่วโมง

## 3. ชั้นป้องกันที่ผู้ดูแลเพิ่มเอง

โปรโตคอลส่งข้อมูลมีลายเซ็น Ed25519 กัน replay และกล่องรับเรื่องเข้ารหัสอยู่แล้ว ชั้นด้านล่างลดโอกาสถูกโจมตีเพิ่ม

- firewall (CSF/iptables/ชุดกฎของ hosting): เครื่อง B รับ `/_saan/push` จาก IP ของเครื่อง A เท่านั้น เครื่อง A รับ `/_saan/inbox` เฉพาะขาออกไป B (ระบบภายในเป็นฝ่ายเรียกเสมอ)
- VPN (WireGuard/Tailscale): ผูกทั้งสองเครื่องในวงเดียวกัน แล้วใช้ที่อยู่ในวงนั้นเป็นปลายทางส่งข้อมูล หน้า `www` ยังเปิดสาธารณะได้ตามปกติ
- Cloudflare: ตั้ง Access (service token) ครอบเส้นทาง `/_saan/*` ของ www ให้ผ่านเฉพาะเครื่อง A และตั้ง Access ครอบ `app.school.ac.th` ทั้งโดเมนสำหรับเจ้าหน้าที่ ระบุ `TRUSTED_PROXIES` ให้ตรงช่วง IP ของ Cloudflare
- เครื่อง A ไม่ต้องเปิดพอร์ตฐานข้อมูลออกนอกเครื่อง เครื่อง B ไม่มีรหัสผ่านฐานข้อมูลของ A และไม่มีเส้นทางเครือข่ายไปฐานข้อมูล A
- ฝั่งหน้าบ้านปิดหน้า login ทั้งหมดอยู่แล้ว (`EditionGate` ตอบ 404) ไม่ต้องเพิ่มกฎบล็อกซ้ำ

## 4. หมุนกุญแจ

ทำเมื่อสงสัยว่ากุญแจรั่ว เปลี่ยนผู้ดูแล หรือเครื่อง B ถูกเจาะ ทำที่เครื่อง A

- `php artisan saan:keys-rotate` เลือกชนิดกุญแจ (push, pull, inbox, unlock) กุญแจ push/pull/unlock เปลี่ยนทันที ต้องจับคู่ใหม่ตามข้อ 2 กุญแจ inbox เดิมถูกเก็บไว้จนดึงซองที่ปิดผนึกด้วยกุญแจนั้นหมด (ดู `school:doctor`)
- ถ้าเครื่อง B ถูกเจาะ: ติดตั้งเครื่อง B ใหม่ทั้งชุด หมุนกุญแจทุกชนิด จับคู่ใหม่ แล้ว `saan:publish --full` เนื้อหาบนหน้าบ้านกู้ได้ทั้งหมดจากระบบภายใน
- ไฟล์กุญแจอยู่ใน `storage/app/private/saan-keys` สิทธิ์ 0600 ห้ามอยู่ใต้ `public/`

## 5. รหัสติดตั้งและชื่อที่ได้จากรหัส

รหัสติดตั้งเป็นตัวอักษร 6 ตัว (a-z และ 2-7) สุ่มตอนติดตั้ง เก็บใน `storage/installed.json` และ `.env` (`SAAN_INSTALL_ID`)

| สิ่งที่ได้จากรหัส | รูปแบบ (ตัวอย่างรหัส `k3m7qa`) |
| --- | --- |
| ฐานข้อมูล (มาตรฐาน) | `saan_k3m7qa_int`, `saan_k3m7qa_pub` |
| ผู้ใช้ฐานข้อมูล (ไม่เกิน 32 ตัวอักษร) | `saan_k3m7qa_i`, `saan_k3m7qa_p` |
| คุกกี้เซสชัน | `saan_k3m7qa_internal`, `saan_k3m7qa_public` (ระบบรวม: `saan_k3m7qa`) |
| prefix แคช ล็อก คิว redis | `saan_k3m7qa_internal_` |
| ไฟล์สำรอง | `saan-k3m7qa-internal-<เวลา UTC>.zip` (ใช้ `school:archive backup <โฟลเดอร์>`) |

ทั้งสองฝั่งบนเครื่องเดียวใช้โฟลเดอร์ `storage/` และ `bootstrap/cache` คนละชุดเสมอ ตัวติดตั้งปฏิเสธถ้าสองโฟลเดอร์แอปชี้ไปที่เดียวกัน (รวมถึง symlink)

### prefix ตาราง (ปิดไว้เป็นค่าเริ่มต้น)

`DB_PREFIX` ว่างโดยปกติ เพราะแยกด้วยฐานข้อมูลอยู่แล้ว ใช้เฉพาะกรณีฐานข้อมูลเดียวที่แยกไม่ได้จริง ๆ เช่น `DB_PREFIX=saan_k3m7qa_` Laravel ใส่ prefix ให้ query และ migration เอง แต่ยังไม่ได้ทดสอบกับคำสั่ง SQL ดิบของโมดูลทุกตัวและ `school:archive` กับแพ็กเกจเสริมของบุคคลที่สาม ใช้ฐานข้อมูลแยกตามรูปแบบมาตรฐานเมื่อทำได้ และห้ามเปิด prefix บนฐานข้อมูลที่มีข้อมูลแล้ว

## 6. สำรองและอัปเดต

- ระบบภายในสำรองอัตโนมัติรายวันเมื่อมี cron (`storage/app/private/backups/auto-ปีเดือนวัน.zip` ตั้งด้วย `SAAN_BACKUP_DAILY_AT` และ `SAAN_BACKUP_KEEP`) หน้าบ้านไม่ตั้งสำรองอัตโนมัติ เพราะสร้างคืนได้ด้วย `saan:publish --full`
- cron ต้องตั้งทั้งสองโฟลเดอร์แอป (หนึ่งบรรทัดต่อโฟลเดอร์ ดูคู่มือหัวข้อ 8.1)
- สำรองแยกตามฝั่ง: `school:archive` สำรองเฉพาะฝั่งของตัวเอง archive ของระบบภายในมีกุญแจลับ (`saan-keys`) พร้อมคำเตือนใน `manifest.json` เก็บแบบเข้ารหัสและห้ามส่งให้หน้าบ้าน archive ของหน้าบ้านมีเฉพาะกุญแจสาธารณะของคู่
- อัปเดตสองเครื่อง: รันแพ็กเกจเดียวกันบนทั้งสองเครื่องทีละเครื่อง ระบบภายในก่อน หน้าบ้านทีหลัง (ติดตั้งแบบมาตรฐานบนเครื่องเดียวใช้ `saan:update --both <zip>` ได้ ระบบจะคืนทั้งสองฝั่งถ้าฝั่งใดล้ม) ปุ่มอัปเดตในหน้าเว็บของระบบภายในแบบมาตรฐานตอบ 409 และให้ใช้คำสั่งนี้แทน เพราะปุ่มอัปเดตได้ฝั่งเดียว
- กู้คืน: `school:archive restore` ปฏิเสธ archive ที่ edition ไม่ตรงกับเครื่อง (ห้ามกู้ archive ระบบภายในหรือระบบรวมลงหน้าบ้านเด็ดขาด) และปฏิเสธเมื่อรหัสติดตั้งต่างกัน เว้นแต่ตั้งใจใส่ `--use-source-install` (รหัส คุกกี้ และ prefix ของเครื่องปลายทางคงเดิม)

## 7. มาตรฐานบนเครื่องเดียว: ต้องแยกสิทธิ์ระบบปฏิบัติการ

ตัวติดตั้งแบบมาตรฐานเขียนไฟล์ของสองฝั่งด้วยผู้ใช้ระบบคนเดียวกัน การแยกฐานข้อมูลกันได้แค่ระดับฐานข้อมูล ถ้าหน้าบ้านถูกเจาะโดยโค้ดที่รันบนเครื่อง และสองฝั่งเป็นผู้ใช้ระบบเดียวกันโดยไม่มี `open_basedir` ผู้โจมตีอ่าน `.env` ของระบบภายใน (รหัส DB และ APP_KEY) และ `storage/app/private/saan-keys/*.secret` ได้ จึงต้องทำอย่างใดอย่างหนึ่งก่อนใช้งานจริง

1. แยกผู้ใช้ระบบ (แนะนำ): ให้ PHP-FPM ของ www รันเป็นผู้ใช้ระบบอีกคน `chown -R <ผู้ใช้ www>` โฟลเดอร์หน้าบ้าน และ `chmod 700` โฟลเดอร์ระบบภายในที่เป็นของผู้ใช้อีกคน ตรวจด้วย `ls -ld` ว่าอ่านข้ามกันไม่ได้
2. อย่างน้อยตั้ง `open_basedir=<โฟลเดอร์หน้าบ้าน>:/tmp` ให้ vhost www ใน DirectAdmin: Domain Setup เปิด PHP open_basedir ต่อโดเมน หรือกำหนด PHP-FPM pool แยก (Custom php-fpm pool) แล้ว reload PHP-FPM

`php artisan school:doctor` เตือน [WARN] เมื่อ (ฝั่งระบบภายใน) เจ้าของ `.env` ของสองฝั่งเป็นผู้ใช้ระบบเดียวกัน, (ฝั่งหน้าบ้าน) `open_basedir` ว่าง และ (ทั้งสองฝั่ง) `.env` หรือ `storage/installed.json` เปิดสิทธิ์เกิน 0600 (`chmod 600 .env storage/installed.json`) doctor ยังปฏิเสธ symlink ใน `storage/` และ `bootstrap/cache` ของหน้าบ้าน และการใช้ `storage/app/private`, `saan-keys`, `framework`, `logs` ร่วมกัน

### host ของผู้ใช้ฐานข้อมูลเมื่อ DB อยู่อีกเครื่อง

ถ้า host ของฐานข้อมูลไม่ใช่ localhost ตัวติดตั้งสร้างผู้ใช้ผูกกับ host ของเครื่องแอปตามที่เซิร์ฟเวอร์ฐานข้อมูลเห็นจริง (`SUBSTRING_INDEX(USER(),'@',-1)`) ไม่ใช่ `%` ถ้าเซิร์ฟเวอร์บอกไม่ได้จึงตกไปใช้ `%` ให้จำกัดพอร์ตฐานข้อมูลด้วย firewall ให้รับเฉพาะ IP ของเครื่องแอป

## 8. ประกาศรายชื่อชื่อเต็ม (F9): เครือข่ายและร่องรอยในไฟล์

- โควตาป้องกันการเก็บรายชื่ออยู่ที่ `saan.notices.*` (ดู config/saan.php) 1 การเข้าชมใช้ 2 คำขอ (challenge + rows หรือ search) เครือข่ายมือถือของไทยและ NAT ของโรงเรียนใช้ IPv4 ร่วมกันหลายเครื่อง (CGNAT) ค่าตั้งต้น `per_net` 60 รองรับราว 30 การเข้าชมต่อ IP ต่อ 10 นาที ในวันประกาศผลที่คนเข้าพร้อมกันมาก ให้เพิ่ม `per_net` และ `per_wide` ก่อนวันประกาศ `per_list` นับเฉพาะคำขอที่ผ่าน Turnstile จึงไม่ถูกคำขอขยะใช้หมด ส่วน `per_net` และ `per_wide` นับทุกคำขอ
- ฝั่งภายในส่งชื่อเต็มเมื่อฝั่งสาธารณะตอบ `caps` ว่ารองรับ `full_name_until` และตั้ง Turnstile แล้วเท่านั้น (ถามใหม่ทุก 10 นาที) ถ้าอัปเดตฝั่งภายในก่อน ให้อัปเดตฝั่งสาธารณะและรัน migration ก่อนจึงจะเห็นชื่อเต็ม ระหว่างนั้นผู้ชมเห็นชื่อปิดบัง
- ข้อจำกัดของ "ไม่มีชื่อเต็มหลังหมดเวลา": การปิดบังทำที่ระดับแถวในฐานข้อมูลสาธารณะ แต่สำเนาระดับไฟล์ที่ถ่ายก่อนหมดเวลายังมีชื่อเต็มตามเดิม ได้แก่ snapshot ของ VM/LVM ไฟล์สำรองฐานข้อมูล และ binlog ของ MariaDB (มี INSERT/UPDATE ของเซลล์ชื่อเต็มตามจำนวนวันของ `expire_logs_days`) จึงต้อง: ปิด binlog บนฝั่งสาธารณะ (`skip-log-bin`) หรือตั้ง `binlog_expire_logs_seconds` ให้สั้น (ไม่เกินช่วง `full_name_until` ที่ใช้) และตั้งอายุสำรองของฝั่งสาธารณะให้สั้นกว่าหรือเท่ากับช่วงนั้น สำเนาที่ถ่ายก่อนหมดเวลาถือว่ายังมีชื่อเต็มจนกว่าจะหมดอายุตามนโยบายสำรอง
- ค้นด้วยเลขทำได้เฉพาะคอลัมน์ "เลขที่สมัคร/เลขที่นั่งสอบ" (4-12 หลัก) ควรเป็นเลขที่ไม่เรียงต่อกัน ถ้าเรียงต่อกันทุกแถว ผู้ไล่ค้นที่ผ่าน Turnstile ได้ทีละแถวยังทำได้ตามโควตา
