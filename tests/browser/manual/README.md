# Manual pipeline: scenarios -> browser run -> manual + audit

One source, two products. A **scenario file** per module describes the real tasks a user does (workflows). The **runner** executes
them in a real Chrome against a throw-away install, takes the pictures, and writes `results.json`. The **generator** turns scenarios +
results + pictures into the illustrated Thai user manual and the honest audit of which modules really work.

Nothing may be called "works" unless a browser did it. A page that renders but whose button does nothing is a failure here.

```
docs/manual/scenarios/<module>.json   written by a person (author)           input
        |  tests/browser/manual/run.py        real Chrome, Playwright
        v
docs/manual/run/results.json   images/<module>/<workflow>-<nn>.webp   failures/...        written by the runner
        |  tests/browser/manual/build.py
        v
docs/manual/th/<module>.md   th/index.md   th/images/   audit.th.md                        generated, do not edit
docs/manual/inventory.json            first-look inventory of the 31 modules (tests/browser/manual/inventory.py)
```

Files in this folder: `run.py` (runner), `build.py` (generator), `manuallib.py` (shared code), `scenario.schema.json` (JSON schema),
`selftest.py` (negative test of the runner), `inventory.py` (module inventory), this README. `tests/` is not part of release packages.

`run.py` arguments: `--base`, `--accounts`, `--scenarios <dir or files>` (default `docs/manual/scenarios`), `--out <dir>` (default
`docs/manual/run`), `--only <module | module.workflow | workflow>` (repeatable; a module id runs all its workflows), `--scheme light|dark`,
`--viewport 1366x900` (a workflow may declare its own, e.g. `390x844`), `--shots on|off`, `--run-id` (reuse the marker of an earlier run),
`--validate-only`. Exit code: 0 all selected workflows work, 1 a workflow failed or is blocked, 2 bad scenario or arguments, 3 could not get the run lock within `--lock-wait` (default 1800 s). Other arguments: `--lock-wait`, `--group <label shown to others while you hold the lock>`.
Environment variables `SAAN_AUDIT_BASE` and `SAAN_AUDIT_ACCOUNTS` can replace the two required arguments.
`SAAN_MANUAL_LOCK=<name>` gives the run its own lock: runs with the same name wait for each other, runs with different names do not. Use it
only when each writer has their own install AND their own `--out` folder (results.json is only safe to share under one lock).

A picture is refused when an account password is visible as text, and also when the page lists several account sign-in names next to the
word "รหัสผ่าน" (the accounts list of the installer). The user-management page does the second by design: put `"logins_ok": true` on its
picture steps (a visible password is still refused), and `mask` anything that is a secret.

Upload fixtures: `cover.png`, `sample.pdf`, `sample.csv`, `sample.txt` are generated by the runner. A writer may add their own small file
(fictional data only; csv, txt, pdf, png, jpg, xlsx, json or zip; lower-case name) to `docs/manual/fixtures/` and name it in `file`, for
example a student list in the registry's import format or a file with deliberate error rows.

A step may carry `dialog_text`: the text typed into a browser `prompt()` that the step opens (a reason asked when voiding or cancelling).
A list (`["มผ", "เหตุผล ..."]`) answers several prompts of the same step in order. Without it a prompt is accepted with empty text.

The target must be a throwaway trial install made for the manual (`http://localhost/saan-audit-070`, or a private playground from
`D:\AI-Project\School\install-trials\manual-playground.ps1 -Name <name>`, which also resets it to a clean state). Never aim the runner at a
demo, dev or customer server: scenarios create, change and delete data.

## Accounts and secrets

`--accounts` is the text file that `layout_audit.py` already reads. The runner maps it to **role keys** (never print the file):

| key | who |
|---|---|
| `admin`, `principal`, `homeroom` (alias `teacher`), `subject`, `finance`, `payroll`, `clerk`, `editor` | staff accounts, key = part of the e-mail before `@` |
| `student1`, `student2` | the two student accounts in file order (student1 = เด็กชายกวิน ธารใส ม.1/1, student2 = ม.5/1) |
| `guardian1`, `guardian2` | guardians (guardian1: กวิน ม.1/1 and อคิน ม.4/1; guardian2: ทอฝัน ม.2/1) |
| `learn1`, `learn4`, `complaint` | not accounts: classroom link codes and a complaint tracking number (`login`/`password` fields hold the code) |
| `anonymous` | no sign-in (public site, or a workflow that shows the sign-in form itself) |

The runner signs in before the first step (not shown in the manual). A workflow that teaches how to sign in uses `role: "anonymous"`,
starts at the sign-in page and types `{{secret:guardian1.login}}` and `{{secret:guardian1.password}}`.

Rules the runner enforces, and the author must not work around:
- `{{secret:<role>.login|password}}` is the only way a credential enters a scenario; a literal password in a scenario is refused by validation.
- Credentials are removed from every message the runner prints or stores (results.json, console, errors).
- Pictures: every `input[type=password]`, `[data-mask]`, `[data-secret]` and `input[autocomplete=one-time-code]` is blurred in the image (Pillow, after the screenshot, the page is not changed).
  Use `mask: [target, ...]` for anything else that must not be readable (a generated temporary password, a code shown once).
- The runner **refuses to capture** a page whose text contains an account password or lists several account logins next to the word password. That step fails with "refused to take the picture".
- `build.py` scans every generated page for the passwords of the accounts file and writes nothing if it finds one.

## Scenario format (one JSON file per module)

File name = module id = `modules/<id>/module.json` id: `docs/manual/scenarios/attendance.json`. Validated first by `scenario.schema.json`
and by extra checks (unique ids, known roles, every workflow has a `verify` block that contains an expect, no emoji, ambiguous targets refused).
`docs/manual/scenarios/attendance.json` is the worked example; copy its shape.

Top level (all required unless marked):

| field | meaning |
|---|---|
| `module`, `title` | module id, Thai name as the manual prints it |
| `area` (optional) | area of school work for the manual index (e.g. `งานวิชาการและงานนักเรียน`) |
| `purpose` | one paragraph: what the module is for |
| `roles` | list: who uses it, Thai, by role |
| `menu` | list: where it is, e.g. `เมนูด้านซ้าย "งานโรงเรียน" > "เช็คชื่อ" (/work#attendance)`; a module without menu entry says so: `ไม่มีเมนู: ...` |
| `prerequisites` | list of `{module, text, workflows?}`: what must exist before; `workflows` (ids of that module) make this module's workflows depend on them |
| `vars` | module variables, usable as `{{name}}` |
| `workflows` | the real tasks (below) |
| `skeleton` | things promised but not implemented (below); `[]` only after you really looked |
| `untested` | implemented features you could not exercise with a browser, and why (printed as `ยังไม่ได้ตรวจ`) |
| `coverage`, `coverage_note` | `"partial"` + Thai note when the scenario covers only part of a big module (web-cms: only the news task). A partial module can never get a verdict above `ใช้ได้บางส่วน`; the note is printed on the page and in the audit |

Workflow:

| field | meaning |
|---|---|
| `id`, `title`, `intro` | kebab-case id, Thai title (a task: "เช็คชื่อห้องเรียนของวันที่ต้องการ"), optional paragraph |
| `role` | account key, or `anonymous` |
| `start` | URL path opened after sign-in (`/work`, `/cms`, `/guardian`) |
| `viewport` | optional `390x844` for a phone workflow |
| `core` | true on the module's main task: if it does not work the verdict is `มีแต่โครง` |
| `depends_on` | workflow ids (same module) or `module.workflow`; the runner runs them first and marks this one `blocked` when they do not work |
| `cleanup` | true: runs last in its module and is never blocked (undoes the data the others created) |
| `vars` | workflow variables |
| `steps` | what the user does |
| `expected` | Thai text printed under "ผลที่ควรเห็น" |
| `verify` | list of `{title, as?, start?, steps}` that prove the task did something (below) |
| `status` | **not written by authors**: the runner writes `works` / `fails` / `blocked` into results.json |

### Steps

`{"do": <action>, "target": {...}, "say": "...", "shot": true, ...}`. A step with `say` appears in the manual as a numbered instruction
(the number is the number drawn in the picture); a step without `say` is only for the runner (waits, preconditions, intermediate taps).
`shot: true` needs `say`; the picture is taken **after** the step's effect is visible and becomes the alt text = `say`.

| action | keys | what it does |
|---|---|---|
| `goto` | `url` | open a path or absolute http URL (hash links such as `/work#attendance` work) |
| `click` | `target` | click; optional `repeat_until: {visible: target, max: n}` clicks again until that element is visible (buttons that cycle states) |
| `fill` | `target`, `value` | set a text/date/month field (dates as `YYYY-MM-DD`, months `YYYY-MM`) |
| `type` | `target`, `value` | key by key (rich-text editors that ignore `fill`) |
| `select` | `target`, `label` or `value` | choose an option of a `<select>` |
| `check` / `uncheck` | `target` | tick boxes |
| `upload` | `target`, `file` | `cover.png`, `sample.pdf`, `sample.csv`, `sample.txt` (generated into `docs/manual/fixtures/`); `via_chooser: true` when the button opens the file chooser (target = the button), otherwise target the `input[type=file]` with `include_hidden` |
| `press` | `key`, optional `target` | keyboard key |
| `hover`, `scroll` | `target` | hover / scroll into view |
| `wait_for` | `target` (+`state`), `url` (regex) or `text` | wait for something |
| `expect` | `that` | assertions with auto-retry (below) |
| `capture` | `target`, `var`, optional `regex`, optional `from_attr` | keep the text (or the attribute, e.g. `href`) of an element in `{{var}}` for later steps of the same workflow |
| `reload`, `close_tab` | | reload; close the new tab and go back to the previous one |
| `note` | `say` | manual-only explanation (may carry a picture of the current screen) |

Extra keys on any step: `timeout` (ms), `settle_ms`, `wait_after: target(s)` (must be visible before the picture), `when: {"equals": [a, b]}` or
`{"not_equals": [a, b]}` (step skipped otherwise; skipped steps are not in the manual), `optional: true` (failure = warning; use almost never),
`dialog: "accept"|"dismiss"` (answer to a browser `confirm()` opened by this step; default accept), `comment` (author remark, never printed).

Wrappers on an action step (the action is performed inside them):
- `expect_download: {ext, kind: csv|text|pdf|png|jpeg|xlsx|zip, min_bytes, contains, name_regex}` - a download must happen; `kind` is checked by file signature, `contains` by content.
- `expect_popup: {url_regex}` - a new tab must open at a matching URL; it becomes the current page until `close_tab`.
- `expect_response: {url_contains, method, status}` - a request must be made and answered with that status.

`expect` conditions (`that` is one object or a list; each object has exactly one of these keys):
`visible: target`, `hidden: target`, `text: "..."` (+`in: target`; whitespace-normalised substring), `not_text`, `value: "..."` + `of: target` (+`contains: true`),
`count: n | {min,max}` + `of: target`, `url: "<regex>"`, `checked`, `unchecked`, `enabled`, `disabled`, `http_status: 200 | [200,302]` + `url` (+`anonymous: true`, a plain GET without cookies).

### Targets: how to find an element

A target is an object. Use the first kind that is stable, in this order:
1. `{"role": "button", "name": "บันทึก"}` - role + accessible name (substring; `exact: true` for whole text). This is what a user sees and what a screen reader reads, so it survives restyling, which the staff UI is going through now.
2. `{"text": "..."}` visible text, `{"label": "วันที่"}` form label, `{"placeholder": ...}`, `{"alt"|"title": ...}`.
3. `{"attr": {"data-save": ""}}`, `{"id": "toast"}` - stable attributes the code sets on purpose.
4. `{"css": "section.att"}` - last resort (layout classes change; use it for containers and for state classes such as `.att-chip.att-absent`).

Narrowing keys: `within: <target>` (search inside), `has_text`, `nth` (0-based), `first: true`, `include_hidden: true`. Only visible elements match unless `include_hidden`.
A target that matches more than one element makes the step fail ("target is ambiguous: N elements") instead of clicking the first one: add `within`, `has_text` or `nth`. A `role` target needs `name`, `has_text`, `nth` or `first`.
The sidebar menu is `{"role": "navigation", "name": "ระบบงานโรงเรียน"}`; click `{"role": "link", "name": "เช็คชื่อ", "exact": true, "within": <that>}`.

### Variables

`{{marker}}` = `ทดสอบคู่มือ <run id>` (put it in every name/note you create so reruns do not collide and a person can find the leftovers), `{{run_id}}`, `{{today}}`,
`{{last_weekday}}` (most recent Mon-Fri on or before today, `YYYY-MM-DD`; `{{last_weekday:2}}` two weekdays further back), `{{next_weekday:N}}` (the Nth Mon-Fri after today, for
things that must lie in the future such as a leave that has not started), `{{month_differs}}` ("1" when that weekday is in the previous month),
`{{secret:role.login|password}}`, `{{var}}` from `vars` or `capture`. Filters: `{{last_weekday|th_short}}` = `13 พ.ย. 2569`, `|th_month`, `|month` = `2026-11`, `|day`, `|iso`.
An unknown variable fails the step; the runner never types `{{x}}` into a form.

### Pictures

`shot: true` plus optional `highlight` (target, list of targets, or `false`; default = the step's target) and `crop`:
`viewport` (default), `page` (whole page), `panel` (nearest enclosing card/form/table of the highlighted element), `tight` (the highlight plus `crop_pad` px, default 120), or a target object (that element plus `crop_pad`, default 24).
Crops are kept between 640x340 and 720 px tall so they stay readable. The highlight is a 3 px ring with white halo and a numbered marker (the manual step number), drawn onto the image with Pillow; the page is never touched. Images are WebP (quality 80, max width 1366) at `<out>/images/<module>/<workflow>-<nn>.webp` (`nn` = step number in the run, verify steps continue the count).
Take the picture on the step that shows the effect: a toast that disappears after 2.6 s is caught with `wait_after: {"id": "toast"}` on the click that causes it.

### Verify: how the run proves the workflow did something

`verify` is a list of blocks `{title, as?, start?, steps}`; it runs only when all steps passed. Every block must contain an `expect`, `wait_for` or `expect_download`, otherwise validation refuses it.
- Same account: `reload`, open the screen again and `expect` the saved value (a toast is not proof).
- Another role: `as: "guardian1"` opens a **fresh** browser context signed in as that role (`start` = its first page) - "the student/guardian sees the effect".
- A report or list: open it and find the new row (use `{{marker}}`).
- A file: `expect_download` with `kind`, `min_bytes`, `contains` on the click that downloads.
- Observable only: the runner has no database access and scenarios contain no SQL.
Verify steps with `say` and `shot` become the pictures under "ผลที่ควรเห็น".

### Cleanup and idempotence

Everything a scenario creates carries `{{marker}}`. A workflow that creates data should be undone by a later workflow in the same file with `"cleanup": true`
(delete the record through the UI, or restore the old value), which runs last in the module and is never blocked, so a failure earlier does not leave dirty data. Where the UI offers no delete, say so in the `untested` or `skeleton` list.
Preconditions are explicit `expect` steps (for example "the student starts as present"): if an earlier run died halfway, the next run fails loudly instead of building on dirty data - run the module's cleanup workflow with `--only <module>.<cleanup-id>` and rerun.
Fixed records seeded in the audit install (students, rooms) are shared by all workers: change only what your scenario created or restore it.

### Skeleton list (author, from reading the code and clicking the screens)

`skeleton` answers "which systems are only a skeleton". Items (id `S1`, `S2`, ...): `promised` (what the UI, menu or `module.json` description says, with file:line or screen), `where`, `observed` (what really happens), `evidence` (file:line read, screen clicked, picture, route list), `confirmed` (true/false), and `confirm_how` when false (printed as `ยังไม่ได้ยืนยัน: ...`).
Count as skeleton: a button that does nothing; a tab that only shows placeholder text; a menu entry without a page; a report that is empty by construction; a setting that is saved but never read; a feature in `module.json` `description` with no route or UI.
Be strict and concrete; write "ยังไม่ได้ยืนยัน" rather than guess. A module with any skeleton item cannot get the verdict `ใช้งานได้`.

## Results and verdicts

`results.json`: `modules.<id>.workflows.<id>` = `{status, run_id, started, finished, seconds, role, viewport, scheme, scenario_sha256, steps[], verify[], error, failed_step, console_errors[], failed_requests[], http_5xx[], js_errors[], warnings_4xx[], dialogs[]}`;
a step = `{n, do, say, status: passed|failed|skipped|not_run|warning, seconds, image, failure_image, error, download, popup, response, dialog, settle_timeout}`.
Status of a workflow: `works` = every step and verify block passed **and** no HTTP 5xx and no uncaught JavaScript error happened during it; `fails` = anything else (step, what was seen, a full-page PNG at `failures/<module>/<workflow>-step<nn>.png`, last console errors and failed requests); `blocked` = a `depends_on` workflow did not work.
Results are merged by workflow into the existing file, keyed by the SHA-256 of the scenario file.

Workflow variables (`capture`) live only inside one workflow; data that must cross workflows is found again through the UI by `{{marker}}`.

Verdict per module (only `build.py` decides, only from a **complete** run: every workflow has a result made from the scenario file as it is now): `ใช้งานได้` (all work, no skeleton item), `ใช้ได้บางส่วน`, `มีแต่โครง` (no workflow works, or a `core` workflow does not), `ยังไม่ได้ตรวจ` (incomplete or stale results, or no scenario). `coverage: partial` caps `ใช้งานได้` at `ใช้ได้บางส่วน`. Edit the scenario and the verdict falls back to `ยังไม่ได้ตรวจ` until the module is run again.

## Writing a scenario: procedure for a worker

1. Read `modules/<id>/module.json` (menu, `description`, `settings_schema`), `src/` (what the controllers and services really do), `routes/*.php`, `public/assets/modules/<id>/*.js` (what the screen renders). List what is promised.
2. Click through every screen of the module in the audit install as the roles that use it (use `--shots on` runs and look at the pictures). Note buttons that do nothing and tabs that show only placeholders: these go to `skeleton`.
3. Write workflows as real tasks, one per thing a user does, with a `verify` that reopens or looks from another role. Mark the main task `core`.
4. `run.py --validate-only`, then run your module, then **open every picture**: each must show what its sentence says, readable, ring on the right element, no password, no cut-off text. Fix `crop`/`highlight` until they do.
5. Write `cleanup` workflows; rerun twice in a row to prove idempotence.
6. `build.py`, read the generated page as a school clerk would, and run `selftest.py` if you changed the runner.

## Traps of the staff UI

- **Hash navigation.** `/work#attendance`, `/cms#compose`, `/operations#...` are one page that renders by hash. Reach a screen by clicking the sidebar link (that is what the manual says), or `goto` the full hash URL; `reload` keeps the hash but resets the screen's own state (the date goes back to today).
- **Date and month pickers.** Chrome is started with `--lang=th-TH`: the field shows `13/11/2026`, but `fill` takes ISO (`2026-11-13`, `2026-11`). Never click the calendar icon. Changing a date re-fetches data: put a `wait_after` on something that only exists once the data is there. Many pages refuse weekends/holidays ("วันนี้เป็นวันเสาร์-อาทิตย์"): use `{{last_weekday}}`.
- **Pages that need a selection first.** Reports and sheets show nothing (or the wrong default) until a classroom/month/student is chosen; always select explicitly so the picture shows the selection.
- **Toasts disappear** (about 2.6 s). Take the picture on the click that causes it with `wait_after`; assert the saved value by reloading, not by the toast.
- **Confirm dialogs** (`confirm()`) are accepted automatically; the text is recorded in `dialogs`. Use `dialog: "dismiss"` on a step to test cancel.
- **File uploads.** Most upload buttons are an `input[type=file]` that is visually hidden: target it with `include_hidden: true` and `upload`; if only a button is visible and the app opens the chooser itself use `via_chooser`.
- **Sticky save bars** and glass headers overlay the page bottom: Playwright scrolls the target into view, but a ring near the bottom may sit under the bar: use `crop: "panel"` or `tight`.
- **Buttons that cycle states** (the attendance row cycles present, absent, late, leave, sick): use `repeat_until` or count the clicks; the accessible name contains the current state, so target with a stable prefix.
- **The sign-in pages**: `/login` (staff), `/student` (code), `/guardian`. The portals stay on the same URL after sign-in; the runner knows the form is gone when the password field disappears.
- **Slow server.** The local Apache + PHP can take 2-5 s per request when other audits run at the same time. The runner waits for in-flight fetch/xhr, aria-busy, "กำลังโหลด" text and running animations (never `networkidle`); a step that waits the full 5 s cap records `settle_timeout` in results.json.
- Data written by one workflow is visible to the next: put shared state in `depends_on`, and never rely on the order of two independent workflows.

## Writer's guide (a fresh agent can follow this without asking)

### Your job in one paragraph
You own a list of units (modules and core areas) in `docs/manual/inventory.json` (`groups[].modules` and `groups[].areas`). For each unit you write
`docs/manual/scenarios/<unit-id>.json`, run it, look at every picture, fix it until the results are true, record what is only a skeleton, and run `build.py`.
You never edit application code (a defect goes into the scenario as an `untested`/`skeleton` item or into your report: page, step, what happened, what was expected),
never touch another writer's scenario, and only change data that your scenario created (shared seeded records: see "Cleanup").

### Naming
- Scenario file = module id (`finance.json`); for a core area use the area id of the inventory (`admin-users.json`, `public-website.json`). `module` inside = file name.
- Workflow id: kebab-case verb phrase of the task (`issue-invoice`, `guardian-pays-by-slip`), unique inside the file. Cleanup workflow: `restore-clean`, `trash-test-data`, ... with `cleanup: true`.
- Picture files are produced by the runner: `images/<module>/<workflow>-<nn>.webp`. Never name or edit pictures by hand.
- Variables: always `{{marker}}` in created names; never a date typed by hand (use `{{today}}`, `{{last_weekday}}`).

### Run, rerun, retarget
```powershell
$env:PLAYWRIGHT_BROWSERS_PATH="$env:USERPROFILE\AppData\Local\ms-playwright"
$py='C:\Users\ChonLaWan\anaconda3\envs\ml313\python.exe'; cd D:\AI-Project\School\school-app
$a=@('--base','http://localhost/saan-audit-070','--accounts','D:\AI-Project\School\.private\saan-audit-accounts.txt')
& $py -I tests\browser\manual\run.py @a --validate-only                       # all scenarios, no browser
& $py -I tests\browser\manual\run.py @a --out docs\manual\run --group G4 --only finance   # THE writer's command: one module, every workflow, pictures on
& $py -I tests\browser\manual\run.py @a --out docs\manual\run --group G4 --only finance.issue-invoice          # one workflow (its depends_on run first)
& $py -I tests\browser\manual\build.py                                        # pages, index, audit, wiki bundle
```
**One run at a time, machine-wide.** `run.py` and `build.py` take a lock file (`%PUBLIC%\saan-manual\run.lock`) before they start Chrome or write anything; it is released on every exit path (and an owner that died leaves a stale lock that the next run takes over). If another writer's run holds it, yours prints one line `[..] waiting for another run, held by <group>/<pid> since hh:mm`, then waits quietly (default 30 minutes, `--lock-wait <seconds>` to change) and starts when the lock is free. If it gives up it prints `[ERR] gave up after ...` and exits with code 3: just start it again. Label your runs with `--group G2` (or `$env:SAAN_MANUAL_GROUP`) so that others can see who holds the lock. `--validate-only` needs no lock.
**Never start Chrome, Playwright or a browser of your own outside `run.py`** (no ad-hoc scripts, no `explore` scripts): the lock is the only thing that keeps five writers from running five Chromes against one slow server.
**Everyone uses the same `--out docs\manual\run`.** A run that selects `--only <module>` replaces only that module's entry in `results.json` (read, merge, atomic write while holding the lock) and only that module's pictures and failure files; other writers' modules stay. `build.py` builds from whatever `results.json` holds, so it never drops a module it did not just run (a module whose scenario was edited and not yet rerun is shown as `ยังไม่ได้ตรวจ` and keeps its older pictures until its next run).
**Learning a module and taking pictures of screens while you write:** there is no separate explore mode. Write a small draft scenario (one workflow with a few steps, `shot: true`, `verify` with one `expect`) and run it with `--only <module>.<workflow>` and `--shots on`: you get the pictures and the failure PNG, through the lock. Draft runs are harmless to the others: they only touch your module's entry. Delete or finish the draft before you report.
The same scenarios run against another install by changing `--base` and `--accounts` only (for example the dev tree with the new look `http://localhost/saan-dev-ui` and its accounts file):
no URL, host or password is written in a scenario. The accounts file must contain the same role keys (see "Accounts and secrets"); the runner stops with a clear message when a key is missing.
Use `--out <other folder>` for a retake so that the audit results are not overwritten; `build.py --results <that>/results.json --out <folder>` builds from it.
Because the pictures will be retaken on a restyled UI, **do not depend on the look**: prefer role + accessible name, labels, ids; use CSS only for the semantic hooks that the module's own JavaScript writes (`att-chip att-absent`, `gp-item`, `desk-content-row`): these come from `public/assets/modules/<id>/*.js`, not from the style sheets. Never use a colour, position, icon or a class that comes from `saan-glass.css`.

### How to judge a verdict
1. `results.json` says what happened: `works` only when every step and verify passed with no 5xx and no JS error. Read `error`, the failure PNG (`run/failures/...`), `console_errors`, `failed_requests`.
2. If a workflow fails, decide which of three it is, and act:
   - runner or scenario fault (wrong locator, missing wait, stale precondition): fix the scenario, rerun. Do not weaken a `verify` to make it pass.
   - application defect (the page does the wrong thing): leave the workflow failing, write the defect in your report (page, step number, what happened, what was expected). The verdict stays honest.
   - nothing implemented (button does nothing, placeholder tab, menu without page, always-empty report, setting never read): add a `skeleton` item with file:line and evidence; write `confirmed: false` plus `confirm_how` when you only suspect it.
3. The verdict itself is produced by `build.py` (see "Results and verdicts"). `ใช้งานได้` needs every workflow `works`, no skeleton item, full coverage. Never write a verdict by hand anywhere.
4. A flaky workflow (passes, fails, passes) is a fault, not a verdict: find the missing wait (`wait_after`) and rerun twice in a row.

### Pictures: rules
- Default viewport `1366x900`; a workflow about phones declares `viewport: "390x844"`. Do not change the default.
- Every picture shows what its sentence says: the element the sentence names is inside the picture and ringed; text is readable (crops are 640x340 to 720 px tall; use `crop: "panel"` for a form or table, `tight` for a button, `viewport` for a whole page); nothing is cut off at an edge; the data the sentence mentions is really on screen (an empty state where rows were expected is a failure of the scenario, add `wait_after`); the picture is taken after the effect (toast, loaded rows).
- Only the mock school (โรงเรียนต้นธารวิทยา) and its fictional people; never a real name, e-mail, phone number or school. If a page shows something that looks real, stop and report it.
- No passwords, one-time codes or tokens: password fields are blurred automatically; use `mask` for anything else (generated passwords, 2FA codes, API keys, pairing codes, signed links). The runner refuses a page that shows an account password.
- **The first step of every workflow that has a picture uses `crop: "viewport"`** (the whole 1366x900 page) so that the reader sees where they are (menu, page title); later steps use `panel` or `tight`.
- At most 1 picture per step; steps that only wait, assert or prepare have no `say` and no picture. A verify block gets a picture only for the final proof.
- After writing, open every picture in `docs/manual/run/images/<module>/` (use the Read tool on the .webp files) and compare it with its `say`. Fix `crop`, `highlight`, `wait_after` until all match.

### Thai text: rules (`say`, `intro`, `expected`, `purpose`)
- Formal, plain, short sentences; address the reader by role ("ครู", "ผู้ดูแลระบบ", "เจ้าหน้าที่การเงิน", "ผู้ปกครอง"), Arabic numerals, no slang, no emoji, no English where a Thai word exists.
- One step = one action. Start with a verb: "เลือกเมนู", "พิมพ์", "เลือก", "กดปุ่ม", "ติ๊ก". Put what happens after the action in a second short sentence ("ระบบแสดงข้อความ ...").
- Name menu paths and buttons exactly as on screen, in straight double quotes: `เลือกเมนู "งานโรงเรียน" > "เช็คชื่อ"`, `กดปุ่ม "บันทึก"`. Copy the label from the screen, never from memory.
- Do not mention the test (no "ตัวรัน", "scenario", "marker") in `say`; `{{marker}}` in a typed value is replaced by a sample text for the reader (the manual shows the real value that is in the picture).
- Never write a password, token or real person. Describe the credential: "พิมพ์รหัสผ่านของผู้ใช้".
- `intro`: when the task is used, who may do it, limits the user must know (for example weekends, edit window). `expected`: what the user sees when done.

### Definition of done for one unit
1. Scenario passes `--validate-only`; every workflow has a role, a `verify` that reopens or looks from another role, and a cleanup where the UI offers deletion.
2. Every screen of the unit was opened as each role that uses it and every main task of `first_look_workflows` (inventory) is a workflow or is explained in `untested`/`skeleton` with the reason.
3. Two complete runs in a row of the unit are green or fail for the same recorded reason (idempotence). No data of yours is left except what the UI cannot delete (say so in `untested`).
4. All pictures were looked at and match their sentences; no password, no real data.
5. `skeleton` was filled after reading `module.json`, `src/`, `routes/` and `public/assets/modules/<id>/` and clicking every tab and button: each item has `promised`, `where` (file:line or screen), `observed`, `evidence`, `confirmed`.
6. `build.py` runs without `[ERR]`; the page `docs/manual/th/<unit>.md` reads well to a school clerk; the unit's row in `docs/manual/audit.th.md` shows its verdict and the evidence lines.
7. Report to the coordinator: verdict, workflows works/fails/blocked, skeleton items, application defects (page, step, what happened, expected), what was not verified, minutes per full run.

### Where the manual is published
`build.py` writes, from `docs/manual/run/` and the scenarios:
- `docs/manual/th/<unit>.md` + `th/index.md` + `th/images/<unit>/*.webp`: the manual pages (Markdown without raw HTML: h2-h4, lists, code, tables, notes, images `images/<unit>/<file>.webp`).
- `docs/manual/audit.th.md`: the audit table with verdict definitions and evidence.
- `docs/manual/wiki-bundle/`: the same pages ready for the project site wiki: `manual/<unit>.md` with front matter (`applies_to`, `reviewed`, `summary`), flat images `images/<unit>-<workflow>-<nn>.webp`, `wiki:manual/<unit>` links, and `index.snippet.json` (the category to add to the wiki index).

Hand-over to the project site (`D:\AI-Project\School\saan-site`, static generator `build.php`, wiki source `content/wiki`): the site owner copies (never edits by script from here)
`wiki-bundle/manual/*.md` to `content/wiki/manual/`, `wiki-bundle/images/*` to `content/wiki/images/`, and merges `index.snippet.json` into `content/wiki/index.json` (one new category `manual`, pages = unit ids); then `php build.php` produces `/wiki/manual/<unit>/` and copies the images to `/wiki/images/`. `applies_to` is read from the VERSION of the install the pictures came from (`--applies-to-file`). The audit (`audit.th.md`) is internal: it is not part of the bundle. Retake the pictures on the final look, then rebuild and hand over again.
